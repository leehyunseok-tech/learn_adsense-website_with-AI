PART 3 · 화면부터 서버리스 기능까지

6

서버리스로 외부 API 연결하기

v0로 그려둔 화면은 아직 껍데기일 뿐입니다. 이 장에서는 실제 날씨 데이터를 가져오는 OPEN API를 고르고, 그 API 키를 안전하게 숨기면서 화면에 진짜 데이터를 입힙니다. API 키 노출은 이 장에서 가장 조심해야 할 부분입니다.

약 25분 예제 3개 연습문제 3문항

이 장을 끝내면 할 수 있는 것

  • 무료·상업적 사용 가능·호출 한도가 넉넉한 날씨 OPEN API를 고를 수 있습니다.
  • Supabase Edge Function으로 서버 없이 외부 API를 호출하는 중계 코드를 만들 수 있습니다.
  • API 키를 코드에 하드코딩하지 않고 Cloudflare 환경변수로 안전하게 관리할 수 있습니다.

6.1 우리에게 맞는 OPEN API 고르는 기준

날씨 기반 옷차림 추천 사이트를 만들려면 먼저 날씨 데이터를 가져올 OPEN API가 필요합니다. 세상에는 수많은 OPEN API가 있지만, 실제로 우리 서비스에 쓸 수 있는 것은 조건이 정해져 있습니다.

첫째, 무료여야 합니다. 둘째, 상업적 사용이 허용되어야 합니다 — 이 사이트에는 나중에 광고를 붙일 예정이기 때문입니다. 셋째, 하루 호출 횟수가 넉넉해야 합니다. 최소 10,000회 이상은 되어야 방문자가 늘어도 안심할 수 있습니다.

마지막으로 초당·분당 호출 제한이 걸려 있는 API도 있으니 유의해야 합니다. 하루 호출 한도는 넉넉해도 짧은 시간에 몰리면 막히는 경우가 있기 때문입니다.

[개념] OPEN API

누구나 정해진 규칙(스펙)에 따라 요청을 보내면 데이터를 돌려주는, 외부에 공개된 서비스 창구입니다.

[비유] 💡 이렇게 생각해 보세요

OPEN API를 고르는 건 배달 대행업체를 고르는 것과 비슷해요. 아무리 배달이 빨라도 요금이 비싸면(유료) 못 쓰고, 우리 가게에서 쓴다고 하면 안 된다고 하면(상업적 사용 금지) 역시 못 써요. 하루에 몇 건까지 처리해주는지(호출 한도)도 꼭 확인해야 해요.

요즘은 ChatGPT나 Grok 같은 AI의 웹 검색 기능을 이용하면 조건에 맞는 API 후보군을 빠르게 알려줍니다. 저자는 이런 방식으로 후보를 추린 뒤 WeatherAPI.com을 최종 선택했습니다. 무료인데다 한 달에 100만 회까지 호출할 수 있어서 개인 프로젝트로는 충분했기 때문입니다.

[주의] 무료 한도만 보고 안심하는 함정

월 100만 회, 일 10,000회 같은 총량 한도가 넉넉해도 초당·분당 제한이 따로 걸려 있으면 트래픽이 몰리는 순간 에러가 날 수 있습니다. API 스펙 문서에서 rate limit 항목을 꼭 확인하세요.

6.2 Supabase Edge Function으로 서버 없이 API 부르기

API 키를 발급받았다고 해서 화면 코드에서 곧바로 WeatherAPI.com을 호출하면 안 됩니다. 브라우저에서 직접 호출하면 키가 그대로 노출되기 때문입니다. 그래서 화면과 외부 API 사이에 서버리스 함수를 하나 세워 대신 호출하게 합니다.

Supabase는 별도의 서버를 직접 운영하지 않아도 이런 중계 함수를 배포할 수 있는 Edge Function 기능을 제공합니다. WeatherAPI.com 스펙 문서를 직접 읽을 필요는 없습니다. 터미널에서 Claude Code에게 문서 링크와 원하는 동작을 알려주면 필요한 코드를 대신 작성해줍니다.

[비유] 🔧 이렇게 생각해 보세요

Edge Function은 손님(사용자) 대신 심부름을 다녀오는 대리인이에요. 손님은 대리인에게 "오늘 날씨 좀 물어봐 줘"라고만 말하고, 대리인이 직접 가게(외부 API)에 가서 물건(데이터)을 받아다 줘요. 손님은 가게 문 열쇠(API 키)를 아예 볼 필요가 없어요.

실제 작업 순서는 다음과 같습니다. 먼저 Supabase에 회원가입하고 새 프로젝트를 만듭니다. Edge Functions → Secrets에 들어가서 WeatherAPI.com에서 발급받은 API 키를 등록합니다. 그다음 Functions 메뉴에서 "Via Editor"를 눌러, Claude Code가 만들어준 Edge Function 코드 (index.ts)를 그대로 복사해 붙여넣고 배포합니다.

배포가 끝나면 Claude Code에게 우리 프론트엔드가 이 Edge Function을 호출할 수 있도록 엔드포인트 주소를 알려주고, 그에 맞게 호출 코드를 수정해달라고 요청합니다.

[AI에게] AI에게 이렇게 시켜보세요

WeatherAPI.com의 현재 날씨 조회 API를 Supabase Edge Function으로 감싸는 코드를 작성해줘. [내 환경] - Supabase 프로젝트를 새로 만들었고 Edge Functions를 쓸 거야. - API 키는 Supabase Secrets에 WEATHER_API_KEY 라는 이름으로 저장해뒀어. [하고 싶은 것] - 도시 이름(또는 좌표)을 쿼리 파라미터로 받아서 WeatherAPI.com의 현재 날씨를 조회하고 필요한 값만 JSON으로 돌려주는 index.ts 코드를 작성해줘. [꼭 지켜줘] - API 키를 코드에 절대 직접 쓰지 말고 Deno.env.get("WEATHER_API_KEY")처럼 환경변수로 읽어줘. - 요청이 실패했을 때 에러 메시지를 알기 쉽게 돌려줘. 마지막에 위험한 곳을 짚어줘.

이런 답이 오면 정상 — 코드 어디에도 실제 키 문자열이 그대로 적혀 있지 않고, Deno.env.get(...)처럼 환경변수를 읽는 형태로만 키를 사용합니다.

[AI 함정] AI가 여기서 틀립니다

AI에게 "빨리 동작하는 코드"만 요청하면, 예시를 간단하게 만들려고 API 키를 코드 안에 그대로 적어 넣는 경우가 많습니다. 당장은 실행이 잘 되기 때문에 이 실수를 코드를 눈으로 훑는 것만으로는 알아채기 어렵습니다.

[X] AI가 준 코드 
// index.ts (Edge Function)
const WEATHER_KEY = "abcd1234efgh5678ijkl";

const res = await fetch(
  `https://api.weatherapi.com/v1/current.json?key=${WEATHER_KEY}&q=Seoul`
);
문제 
· 이 파일이 Github Public Repository에 올라가면 키가 그대로 노출됨
· 키가 유출되면 다른 사람이 내 호출 한도를 다 써버릴 수 있음
[O] 고친 코드 
// index.ts (Edge Function)
const WEATHER_KEY = Deno.env.get("WEATHER_API_KEY");

const res = await fetch(
  `https://api.weatherapi.com/v1/current.json?key=${WEATHER_KEY}&q=Seoul`
);

이걸 잡아낸 개념 — 6.3절의 "API 키는 코드가 아니라 환경변수로 관리한다"는 원칙입니다.

6.3 API 키를 Cloudflare 환경변수에 안전하게 숨기기

Edge Function 쪽 키는 Supabase Secrets로 숨겼지만, 프론트엔드(FE)가 Edge Function을 호출할 때도 Supabase API 키(anon public)가 하나 더 필요합니다. Project overview 화면에서 이 키를 복사할 수 있습니다.

여기서 절대 하지 말아야 할 것은, 이 키를 사이트 코드 안에 문자열로 직접 적어 넣는 것입니다. FE 코드는 브라우저에 그대로 내려가므로, 누구나 개발자 도구로 코드를 열어보면 키를 볼 수 있습니다. 사이트를 배포하는 Cloudflare의 환경변수에 키를 저장해두고, 코드에서는 그 변수 이름만 참조해야 합니다.

[비유] 💡 이렇게 생각해 보세요

API 키를 코드에 직접 적어 넣는 건 집 열쇠를 현관문 앞에 붙여두는 것과 같아요. 문은 잠갔지만 열쇠가 바로 옆에 있으니 누구나 열 수 있는 거예요. 열쇠는 따로, 안전한 곳(환경변수)에 보관해야 진짜 잠긴 거예요.

변수 이름은 원하는 대로 정해도 되지만, 실제 코드에서 그 이름을 정확히 사용하고 있는지 반드시 확인해야 합니다. 이름이 하나라도 다르면 배포 후에 값을 못 찾아서 API 호출이 조용히 실패합니다.

6.4 Claude Code로 화면에 진짜 데이터 입히기

API 키를 안전하게 숨기는 구조까지 갖췄다면, 이제 Claude Code에게 화면 컴포넌트가 Edge Function을 호출해 실제 날씨 데이터를 받아오도록 수정을 요청합니다. 이전까지 목업(mock) 데이터로 채워져 있던 화면이, 이 단계를 거치면 실제 API 호출 결과로 바뀝니다.

데이터를 연결한 뒤에는 로딩 중 표시, 에러 발생 시 안내 문구처럼 유저 친화적인 부분도 함께 다듬습니다. 이렇게 완성한 화면이 이 책 예제의 최종본에 가까운 모습입니다.

이 장에서 배운 것

  • 무료·상업적 사용 가능·넉넉한 호출 한도라는 세 가지 기준으로 OPEN API를 골랐습니다.
  • Supabase Edge Function을 대리인 삼아, 브라우저 대신 서버리스 함수가 외부 API를 호출하도록 만들었습니다.
  • API 키는 코드에 절대 직접 적지 않고, Supabase Secrets와 Cloudflare 환경변수에 나누어 보관했습니다.

외부 API를 부를 땐 키를 코드가 아니라 환경변수에 숨기는 것이 핵심입니다.

연습문제

1. 우리 사이트에 쓸 OPEN API를 고를 때 반드시 확인해야 할 조건 세 가지를 쓰세요. 쉬움

정답 보기

무료여야 하고, 상업적 사용이 허용되어야 하며(광고를 붙일 예정이므로), 호출 횟수 한도가 넉넉해야 합니다(하루 10,000회 이상). 이 세 조건 중 하나라도 빠지면 서비스를 운영하는 도중 문제가 생길 수 있습니다.

2. 브라우저가 WeatherAPI.com을 직접 호출하지 않고 Supabase Edge Function을 거치도록 만드는 이유는 무엇인가요? 보통

정답 보기

브라우저에서 직접 API를 호출하면 API 키가 화면 코드 안에 그대로 담겨서 개발자 도구로 누구나 볼 수 있게 됩니다. Edge Function이 대리인 역할을 하면 키는 서버 쪽(Secrets)에만 남고 브라우저는 결과만 받습니다.

3. 하루 호출 한도가 넉넉한 무료 API를 쓰는데도 배포 직후 트래픽이 몰리는 순간에만 API 호출이 실패한다면, 무엇을 의심해봐야 할까요? 어려움

정답 보기

초당 또는 분당 호출 제한(rate limit)에 걸렸을 가능성이 큽니다. 하루 총량 한도와 짧은 시간 단위 제한은 별개이므로 API 스펙 문서에서 둘 다 확인해야 합니다.
