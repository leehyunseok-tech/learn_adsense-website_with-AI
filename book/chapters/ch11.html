PART 5 · 브랜딩과 수익화

11

사이트 품질 높이고 승인률 올리기

이 책의 마지막 실습 장입니다. Lighthouse로 사이트 품질을 점검하고, 애드센스 반려의 가장 흔한 사유인 콘텐츠 부족에 대응하고, JSON-LD와 서치콘솔로 지금까지 만든 사이트를 마무리합니다.

약 18분 예제 2개 연습문제 3문항

이 장을 끝내면 할 수 있는 것

  • Lighthouse로 사이트의 성능·접근성·SEO 점수를 점검하고 개선할 수 있습니다.
  • "게시자 콘텐츠가 없는 화면" 반려 사유에 맞춰 사이트에 설명 글과 페이지를 보강할 수 있습니다.
  • JSON-LD를 추가하고 서치콘솔로 유입 키워드를 확인하며 사이트 방향을 점검할 수 있습니다.

11.1 Lighthouse로 품질 점검하기

사이트를 만들고 배포했다면, 얼마나 빠르고 안정적으로 동작하는지 점검하는 게 좋습니다. Lighthouse(라이트하우스)는 웹사이트 품질을 측정하는 도구로, 성능·접근성·SEO(검색엔진최적화) 등을 점수와 함께 시각적으로 분석해 줍니다.

[개념] Lighthouse

구글이 만든 웹사이트 품질 측정 도구입니다. 성능, 접근성, 권장사항, SEO 네 가지 영역을 0~100점으로 채점하고, 점수가 낮은 항목마다 구체적인 개선 제안을 함께 보여줍니다.

[비유] 💡 이렇게 생각해 보세요

Lighthouse 점수는 건강검진 결과표 같아요. 어디가 아픈지 스스로는 잘 못 느껴도, 검진표를 보면 "이 수치가 낮으니 여길 신경 써야겠다"는 게 한눈에 보이잖아요. 사이트도 마찬가지로, 점수표를 보면 어디부터 손봐야 할지 바로 알 수 있어요.

검색해서 Lighthouse를 사용해 보는 것을 추천합니다. 사이트 품질은 애드센스 승인에도 영향을 미칠 수 있으므로, 심사를 요청하기 전에 한 번쯤 점검해 두면 좋습니다.

[주의] 점수만 보고 안심하는 함정

Lighthouse 성능 점수가 높다고 해서 애드센스 승인이 보장되는 건 아닙니다. 점수는 기술적인 품질만 측정할 뿐, 다음 절에서 다룰 콘텐츠 부족 같은 문제는 따로 점검해야 합니다.

11.2 콘텐츠가 부족하다는 반려 사유 대응하기

애드센스 승인 심사에서 가장 흔한 반려 사유 중 하나가 "게시자 콘텐츠가 없는 화면에 Google 게재 광고"입니다. 만든 웹사이트가 단일 페이지로, 실질적인 글이나 설명 없이 데이터만 보여주는 형태라면 사용자가 머물 이유가 없다고 판단되어 광고 게재가 승인되지 않습니다.

[비유] 🔧 이렇게 생각해 보세요

데이터만 있는 페이지는 숫자만 적힌 전광판 같아요. "오늘 기온 15도"만 뜨면 볼 건 다 봤으니 바로 나가버리죠. 그런데 "15도면 이런 옷차림이 좋아요, 어제보다 3도 낮으니 겉옷을 챙기세요" 같은 설명이 붙으면 사람들이 좀 더 머물게 돼요.

이 반려 사유를 해결하려면 텍스트, 설명, 비교, 해석, 팁처럼 사용자의 이해를 돕는 글을 반드시 포함해야 합니다. 혹은 단일 페이지로는 콘텐츠 양이 부족하므로, NavigationBar 컴포넌트를 추가하고 3~5개 이상의 유의미한 다른 페이지를 만들어 사이트 전체의 콘텐츠 양을 늘리는 것도 좋은 방법입니다.

[AI에게] AI에게 이렇게 시켜보세요

Lighthouse에서 이 항목들이 낮게 나왔어. 개선 방법을 알려줘. [내 환경] Next.js 프로젝트, 배포는 Cloudflare Pages야. Lighthouse 결과: 성능 68점, 접근성 82점, SEO 75점. 지적된 항목: 이미지 크기 미지정, 메타 설명 누락, 대비 부족 텍스트. [하고 싶은 것] - 각 항목이 왜 감점됐는지 설명해줘 - 코드로 바로 고칠 수 있는 부분부터 알려줘 [꼭 지켜줘] - 애드센스 승인에도 영향이 갈 수 있는 항목이면 우선순위를 높여줘 마지막에 위험한 곳을 짚어줘.

이런 답이 오면 정상 — 항목별 원인을 짚고, 이미지 width/height 지정이나 메타 설명 추가처럼 구체적인 코드 수정 위치를 알려줍니다.

[AI 함정] AI가 여기서 틀립니다

JSON-LD 구조화 데이터를 추가해 달라고 하면, AI가 만든 JSON을 <script type="application/ld+json"> 태그 밖에 일반 텍스트나 주석으로 넣어버리는 경우가 있습니다. 화면에는 아무것도 안 보이니 잘못 넣은 걸 눈으로는 알아채기 어렵고, 검색엔진은 이 데이터를 아예 인식하지 못합니다.

[X] AI가 준 코드 
<!--
{ "@context": "https://schema.org", "@type": "WebSite" }
-->
문제 
· 검색엔진이 구조화 데이터를 읽지 못함
· 서치콘솔의 구조화 데이터 리포트에 아무것도 안 잡힘
[O] 고친 코드 
<script type="application/ld+json">
{ "@context": "https://schema.org", "@type": "WebSite" }
</script>

이걸 잡아낸 개념 — 11.3절에서 다루는 서치콘솔의 구조화 데이터 확인 기능이 이런 누락을 잡아냅니다.

11.3 JSON-LD와 서치콘솔로 마무리하기

JSON-LD(JavaScript Object Notation for Linked Data)는 우리가 만든 사이트가 어떤 사이트인지에 대한 정보를 구조화한 것입니다. JSON-LD를 활용해 웹사이트 소개 정보를 구조화하면 검색엔진이 웹사이트를 더 잘 이해하고, 사용자에게 더 정확한 정보를 제공할 수 있습니다.

그동안 연동했던 검색엔진들, 즉 구글 서치콘솔 같은 도구에서는 어떤 검색어로 사이트에 유입되고 있는지 확인할 수 있습니다. 의도한 키워드로 실제 유입이 되고 있는지 주기적으로 확인하면서, 앞으로 사이트를 어떤 방향으로 키워 갈지 판단하는 데 큰 도움이 됩니다.

1장부터 여기까지, 아이디어를 정하고 아키텍처를 잡고 AI와 함께 개발하고 배포하고 광고까지 붙였습니다. 결국 우리가 만든 건 하루짜리 결과물이 아니라, 계속 데이터를 받고 콘텐츠를 늘리고 검색엔진과 대화하는 시스템입니다.

이 장에서 배운 것

  • Lighthouse로 성능·접근성·SEO 점수를 확인하고 개선 방향을 잡는 법을 익혔습니다.
  • "게시자 콘텐츠가 없는 화면" 반려 사유에 맞춰 설명 글과 다른 페이지를 늘리는 법을 배웠습니다.
  • JSON-LD와 서치콘솔로 사이트 정보를 구조화하고 유입 키워드를 점검하는 법을 익혔습니다.

1장부터 11장까지, 우리가 만든 것은 하루짜리 결과물이 아니라 시간이 아닌 시스템이 돈을 버는 구조였습니다.
